# AGENTS.md

Instructions for AI agents working in this Node.js codebase.

`node-cooper` is a JavaScript port of [`cooper`](https://github.com/joetjen/cooper),
an Elixir library that loads CASC config files. `guides/casc/CASC.md`
(vendored unchanged from `@joetjen/cooper`'s own `guides/casc/`) is the normative,
implementation-independent language spec. The reference implementation
is the authority: this port behaves exactly like it, except where a
difference is inherent to the host language, and each such difference is
recorded in `test/conformance/DIVERGENCES.md`. Where the reference and
the spec disagree, the fix goes to the reference (and its spec) first,
and this port follows.

The loaded *value model* mirrors `cooper`'s shape-per-type choices as
closely as JS allows, so someone who knows one implementation recognizes
the other. Where it deviates on purpose (integers are `number` up to
`Number.MAX_SAFE_INTEGER`, then `bigint`; atoms are `Symbol.for(name)`;
a loaded float is a plain `number`, though a consumer's tag is handed a
`CooperFloat`), the reason is documented in the value's own module and
in `DIVERGENCES.md`, not left implicit.

## Communication

- Every response starts with the user's first name. Determine it from
  `git config user.name` (take the first name); if that's unavailable
  or ambiguous, ask once. Remember the answer for the rest of the
  session rather than re-deriving or re-asking.

## Before every commit

- Run `npm run precommit` (type-check via `tsc --checkJs --noEmit`,
  then the full test suite) and make sure it passes. No exceptions.

## Language: plain JS + JSDoc, not TypeScript

- Source is plain `.cjs`/`.js`. No `.ts` files and no build step.
  Type safety comes from JSDoc `@typedef`/`@param`/`@returns`
  annotations checked by `tsc --checkJs --noEmit` (`npm run typecheck`).
- Keep JSDoc annotations current with the code they describe.
  `tsc --checkJs` catches drift in signatures, but not in prose.

## Conformance with the reference implementation

- `test/conformance/cases/*.casc` are run through both implementations.
  `<case>.expected.json` is the Elixir reference's result, generated by
  `scripts/oracle.exs` (`npm run oracle`, which needs a `cooper` checkout
  in `../cooper` and Elixir installed). **Never hand-edit an
  `.expected.json`.** Add or change the `.casc` file and regenerate.
- A behavior change needs a conformance case, not just a unit test.
  Only a result that can differ solely because of the host language
  would get a `<case>.node.json` with this port's result, plus a row in
  `DIVERGENCES.md`, in the same change. Today there are none. The one
  Node-only load option the corpus runs with is `modules` (a Node
  module is a location, so `!module` needs a mapping; see
  `test/conformance/options.js`).
- Any other disagreement with the reference is a bug to fix, never an
  override: in this port, or, if the reference is the one at fault, in
  the reference first. Never introduce a divergence silently.

## Tests

- Tests must stay current with behavior. A change to what code does
  needs its tests updated in the same commit, not "later". A passing
  suite that no longer exercises real current behavior is worse than a
  failing one.
- Add tests for new behavior as you write it, not as a follow-up.
- Tests live in `test/`, split by concern (`values/`, `grammar/`,
  `pipeline/`, `conformance/`), and run via Mocha/Chai (`npm test` /
  `npm run autotest` to watch). Unit tests pass `dotenv: false` and an
  explicit `env`, so the developer's own environment can't leak in.
- Where inputs form a space bigger than a handful of examples usefully
  covers (parsers, literals, merge logic, anything with an invariant
  that should hold for *all* inputs), prefer a property-based test
  (`fast-check`, this project's analog of Elixir's `stream_data`) over
  enumerating more example cases by hand. Use ordinary example-based
  tests for fixed, specific scenarios and regressions.
- `test/SPEC_COVERAGE.md` maps every CASC.md section to its tests.
  Update it in the same change as the coverage it tracks.

## Documentation

- Treat every documentation surface touched by a change as part of
  that change, not optional polish: JSDoc, README, guides, changelog,
  `DIVERGENCES.md`, and code comments explaining non-obvious behavior.
  None of it is allowed to go stale.
- Every exported class/function needs a JSDoc block. Update it whenever
  behavior changes. Stale docs are worse than none.
- `guides/casc/` is vendored from `@joetjen/cooper` and stays identical to it.
  Language changes go to the reference's spec first.
- Update `CHANGELOG.md` for every user-facing change, following
  [Keep a Changelog](https://keepachangelog.com/):
  - Add entries under `[Unreleased]` as you work.
  - Releases are cut with `npm version <major|minor|patch>`, which runs
    `auto-changelog` to regenerate the file from commit history and move
    `[Unreleased]` under a version heading. Don't hand-roll that step.

## Dual entry points (ESM/CJS parity)

- `src/*.cjs` is the real implementation, in plain CommonJS so it can
  also be `require()`d directly. **This is the file to change** for
  any behavioral fix or feature.
- `src/*.js` is the ES Module entry point, a thin wrapper. If you add
  or rename an export, update both files so they keep exporting the
  same API, and add/adjust a test against both entry points before
  calling a change done.

## Sync and async (one pipeline, two drivers)

- Pipeline stages that may call user code (import-scheme loaders,
  resolvers, tags) are generator functions that `yield` an effect
  (`src/pipeline/effects.cjs`). `runSync`/`runAsync` drive the same
  generator for the `*Sync` and Promise-returning APIs. Don't write a
  second copy of a stage for one flavor. Call user code only through
  `call()`, and test any new extension point under both drivers.

## Naming

- Value classes are unprefixed (`Secret`, `Tuple`, `Duration`,
  `ByteSize`, `IPv4`, `IPv6`, `LocalDate`, ...). Acronyms stay uppercase
  (`IPv4`, not `Ipv4`). File names are lowercase-kebab (`byte-size.cjs`
  exports `ByteSize`).
- Any value class with a close native JS counterpart gets two-way
  conversion helpers: a `toX()` instance method and a static `fromX()`.
  Where no close native fit exists, omit the helpers and say why in that
  class's own JSDoc, rather than forcing a misleading one.

## Dependency boundaries

- Zero runtime dependencies unless truly justified. New packages belong
  in `devDependencies` only by default. The CASC lexer/parser, the
  `.env` parser and the import glob matcher are hand-rolled specifically
  to keep this boundary. If you're tempted to add a runtime dependency,
  stop and flag it instead.

## Generated/checked-in code

- `test/conformance/cases/*.expected.json` are generated by
  `scripts/oracle.exs`. See "Conformance" above.
- `CHANGELOG.md` is generated by `auto-changelog` (via `npm version`).
  Don't hand-edit released sections; only append to `[Unreleased]` by
  hand while working.

## Git workflow

- Use [git flow](https://nvie.com/posts/a-successful-git-branching-model/):
  `main` (releases), `develop` (integration), `feature/*`,
  `release/*`, `hotfix/*`, `support/*`.
- No direct commits to `main` or `develop`. Branch, then merge/PR back.
- Before starting work, check out onto a git flow branch (`feature/*`,
  `release/*`, `hotfix/*`, `support/*`). Never work directly on
  `develop` unless explicitly told to.

## Commits

- Use [Conventional Commits](https://www.conventionalcommits.org/):
  `<type>[optional scope]: <description>`.
- Common types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`,
  `test`, `chore`, `build`, `ci`.
- Breaking changes: `!` after type/scope, or a `BREAKING CHANGE:` footer.

## Versioning

- Use [Semantic Versioning](https://semver.org/): `MAJOR.MINOR.PATCH`.
- `MAJOR` for breaking changes, `MINOR` for backward-compatible features,
  `PATCH` for backward-compatible fixes.
- Bump the version with `npm version <major|minor|patch>`, which updates
  `package.json` and regenerates `CHANGELOG.md` via `auto-changelog`,
  as part of the release.
